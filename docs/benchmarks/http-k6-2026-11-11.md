# Benchmark HTTP con k6 — Baseline T1

| Campo | Valor |
|---|---|
| **Proyecto** | ZenBet — API `Zenbet.EventsMarkets.Api` |
| **Ejecutado** | 2026-11-11, 18:14–18:26 (hora local, UTC−04:00) |
| **Host** | Intel Core i9-12900K (16 núcleos / 24 hilos), 32 GB RAM, Windows 11 Pro build 26200 |
| **Runtime** | Docker Desktop 29.6.2 (WSL2, 15,49 GiB asignados a la VM), Compose 5.3.1, k6 v2.3.0, Node v24.21.0 |
| **Commit** | `0dd8625` (`origin/main`) |
| **Stack** | `docker compose --profile full` aislado (`zenbet-t1`), API en `:15005`, Postgres 16 en `:55432` |
| **Datos** | 200 usuarios × 1000 € demo, 48 mercados abiertos, 200 apuestas pendientes para cash out |
| **Artefactos** | `loadtest/results/*.json` (summary-export), `*-stats.csv` (CPU/RAM), `run.log` |

> **Cautela:** k6, el API y PostgreSQL corren en **el mismo host**. El cliente de carga compite
> por CPU y memoria con el servidor, así que las cifras sirven para **comparar escenarios entre
> sí y localizar cuellos**, no como capacidad de producción ni como techo de throughput.

---

## 1. Resumen ejecutivo

Se midió el API por HTTP real contra Kestrel, sin proxy intermedio. El baseline produce
**0 errores y 0 HTTP 429 fuera del escenario de mercado caliente**, pero **el SLO propuesto
falla de forma severa bajo contención de un solo mercado**.

| Escenario | Reqs | req/s | p50 | p95 | p99 | Error | 503 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `read-events` (50 VUs) | 11 356 | 188,5 | 10,1 ms | 22,8 ms | 37,6 ms | 0,00 % | 0 |
| `bet-distinct` (200 VUs / 48 mercados) | 6 900 | 111,7 | 1 404,9 ms | 3 030,1 ms | 3 664,6 ms | 0,00 % | 0 |
| `bet-hot-market` (200 VUs / 1 mercado) | 3 926 | 114,3 | 190,0 ms | 4 321,8 ms | 5 121,4 ms | **94,93 %** | 3 727 |
| `cashout` (ráfaga de 200) | 200 | — | 108,9 ms | 127,2 ms | 130,8 ms | 0,00 % | 0 |

**Veredicto del SLO propuesto:**

- Lecturas: ✅ **cumple** (p95 22,8 ms ≪ 100 ms; 0 % de error).
- Apuestas repartidas entre mercados: ❌ **no cumple** latencia (p95 3 030 ms > 500 ms), aunque
  sin errores.
- Mercado caliente (200 VUs sobre un mercado): ❌ **no cumple** de forma extrema: p95 4 321,8 ms,
  **94,93 % de respuestas 503** y solo 199 apuestas aceptadas en 30 s (≈ 6,6/s).
- Cash out: ✅ **cumple** (200/200 en una ráfaga, p95 127,2 ms).

El 503 no es una caída: es el *fail-fast* intencional de `MarketBetGate.EnterAsync`
(`backend/.../Concurrency/MarketBetGate.cs:63`, commit `0923dcd`) para no agotar el pool de
PostgreSQL. El benchmark confirma que el mecanismo **protege la base de datos**, pero deja
≈ 19 rechazos por cada apuesta aceptada bajo esa contención.

## 2. Metodología

1. **Stack aislado.** `loadtest/compose.bench.yml` redefine puertos, nombre de contenedores,
   volumen y red (`zenbet-t1`). No comparte recursos con el stack de desarrollo/QA.
2. **Datos deterministas.** `loadtest/seed.mjs` registra 200 usuarios a **4 req/s** (límite por
   IP de `/api/auth/*`), acredita 1000 € demo a cada uno y crea una apuesta pendiente por
   usuario para el escenario de cash out. Los tokens quedan en `loadtest/.runtime/` (ignorado
   por git) y se reutilizan en todas las iteraciones: ningún escenario llama a auth.
3. **Carga.** Cuatro escenarios k6 secuenciales, sin solapamiento, con `sleep` de 0,25 s en los
   tres primeros para mantener una tasa estable y no un *spin* puro.
4. **Instrumentación.** `lib/metrics.js` separa la latencia de respuestas exitosas
   (`ok_duration`) de la de rechazos, y cuenta 429/503/5xx por separado.
5. **Recursos.** `docker stats --no-stream` cada 2 s sobre `zenbet-t1-backend` y
   `zenbet-t1-postgres` durante cada escenario.

Comando ejecutado:

```powershell
docker compose -p zenbet-t1 -f docker-compose.yml -f loadtest/compose.bench.yml --profile full up -d --build
pwsh loadtest/run-baseline.ps1
```

> **Alcance:** las mediciones son **directas a Kestrel** (`localhost:15005`). No incluyen nginx,
> TLS ni la latencia de red de un cliente real. Son una cota inferior del tiempo de respuesta
> percibido.

## 3. Lecturas y compresión (`read-events`)

`GET /api/v1/events?pageSize=50`, 50 VUs durante 60 s.

| Métrica | Valor |
|---|---:|
| Peticiones | 11 356 (188,5 req/s) |
| p50 / p95 / p99 | 10,1 / 22,8 / 37,6 ms |
| Máximo | 114,5 ms |
| HTTP 200 | 11 356 (100 %) |
| Respuestas comprimidas | 11 356 / 11 356 (100 %) |

**Compresión verificada** con una petición independiente (`pageSize=50`, mismo payload):

| Codificación | Bytes | Reducción |
|---|---:|---:|
| `identity` | 162 378 | — |
| `gzip` | 28 606 | **−82,4 %** |
| `br` | 56 148 | **−65,4 %** |

Durante la corrida k6 el servidor negoció **Brotli** (`Accept-Encoding: gzip, br` →
`Content-Encoding: br`), es decir, el escenario midió la variante del −65,4 %. Gzip comprime
mejor en este payload porque ASP.NET Core usa `CompressionLevel.Optimal` para gzip y
`CompressionLevel.Fastest` para Brotli por defecto (`Program.cs:148-152`, sin overrides). No se
modificó el código: es una observación de configuración, no un defecto del benchmark.

**Lectura del resultado:** con 50 VUs y `sleep 0.25`, la tasa está marcada por el cliente
(50 / (0,25 + 0,012) ≈ 190 req/s), no por el servidor. El escenario demuestra latencia baja y
compresión al 100 %, **no** el techo de lectura del API.

## 4. Apuestas repartidas (`bet-distinct`)

200 VUs durante 60 s, cada VU apuesta a un mercado distinto según `(VU−1) mod 48`; con 48
mercados abiertos, cada mercado recibe ~4 VUs.

| Métrica | Valor |
|---|---:|
| Peticiones | 6 900 (111,7 req/s) |
| p50 / p95 / p99 | 1 404,9 / 3 030,1 / 3 664,6 ms |
| Máximo | 5 087,2 ms |
| HTTP 201 | 6 900 (100 %) |
| 429 / 503 / 5xx | 0 / 0 / 0 |

**Lectura del resultado:** no hay rechazos, pero la latencia es alta y estable: la cola de
serialización por mercado (gate + transacción de wallet/ledger) domina. Con 4 VUs por mercado,
p95 ≈ 3 s indica que el cuello no es el gate de contención extrema, sino el coste por apuesta
bajo concurrencia. El throughput coincide con el ritmo del cliente
(200 / (0,25 + 1,52) ≈ 113 req/s), así que tampoco es un techo puro de servidor.

## 5. Mercado caliente (`bet-hot-market`)

200 VUs durante 30 s, todas al mismo mercado (`Gane vs. Hokit / Ganador`).

| Métrica | Valor |
|---|---:|
| Peticiones | 3 926 (114,3 req/s) |
| p50 / p95 / p99 | 190,0 / 4 321,8 / 5 121,4 ms |
| Máximo | 5 759,2 ms |
| HTTP 201 | 199 (5,07 %) |
| HTTP 503 | **3 727 (94,93 %)** |
| 429 / otros 4xx | 0 / 0 |
| p50 / p99 solo 2xx | 4 132,5 / 4 973,4 ms |

La distribución es bimodal: la mediana (190 ms) la marcan los rechazos rápidos del gate (los
2xx tienen p50 4 132,5 ms), mientras la cola (p95 > 4 s) son las peticiones que esperan turno.
Aun mirando solo las respuestas exitosas, el p95 es 4 576,5 ms: **el incumplimiento del SLO no
depende de contar los 503**.

Los 503 están confirmados en los logs del backend como `ServiceBusyException`
("El mercado está recibiendo demasiadas apuestas a la vez…"), lanzada por
`MarketBetGate.EnterAsync` en `MarketBetGate.cs:63`. Capacidad observada en esa ventana:
**≈ 6,6 apuestas aceptadas/s** y ≈ 124 rechazos/s.

**Conclusión:** el *fail-fast* funciona como protección (PostgreSQL no se agota, no hay 5xx
distintos de 503), pero la experiencia bajo un mercado caliente es de rechazo masivo, no de
degradación elegante.

## 6. Cash out (`cashout`)

200 VUs, una iteración cada una (ráfaga única), cada una sobre una apuesta pendiente distinta.

| Métrica | Valor |
|---|---:|
| Peticiones | 200 (todas en ~150 ms) |
| p50 / p95 / p99 | 108,9 / 127,2 / 130,8 ms |
| Máximo | 131,3 ms |
| HTTP 200 | 200 (100 %) |

La dispersión es mínima (min 82,1 ms, max 131,3 ms) y no hay rechazos. **El `req/s` de k6
(1 340,8) no es throughput sostenido**: es 200 / 0,149 s, la duración de la ráfaga. No se
muestrearon recursos porque la ráfaga termina antes del primer muestreo (2 s).

## 7. CPU y RAM

Picos por escenario (`docker stats`, muestreo cada 2 s):

| Escenario | Backend CPU | Backend RAM | Postgres CPU | Postgres RAM |
|---|---:|---:|---:|---:|
| `read-events` | 215,8 % | 214 MiB | 103,8 % | 146 MiB |
| `bet-distinct` | **1 826,5 %** | 681 MiB | 414,7 % | 322 MiB |
| `bet-hot-market` | 1 655,4 % | **4,37 GiB** | 357,4 % | 315 MiB |
| `cashout` | sin muestras (ráfaga < 2 s) | — | — | — |

Dos lecturas relevantes:

1. **El camino de apuestas quema CPU de forma desproporcionada.** ~1 700–1 800 % equivale a
   ~17–18 hilos de los 24 lógicos del host. A 110–114 req/s, el coste es de decenas de hilos
   por cada 100 apuestas/s, muy por encima de lo que sugiere el throughput.
2. **El mercado caliente dispara la RAM del backend a 4,37 GiB** (20× la línea base de 214 MiB),
   aunque el rechazo sea *fail-fast*. La contención se traduce en memoria retenida, no en
   trabajo útil.

PostgreSQL se mantiene por debajo de ~4,2 núcleos en todos los casos, consistente con que el
cuello está en el proceso .NET y no en la base.

## 8. SLO propuesto y veredicto

Propuesta para discutir (no existe un SLO formal en el repo):

| Objetivo | Umbral | Medido | Veredicto |
|---|---|---|---|
| `GET /events` p95 | < 100 ms, error < 0,1 % | 22,8 ms, 0 % | ✅ |
| `POST /bets/place` p95 (≤ 4 VUs/mercado) | < 500 ms, error < 1 % | 3 030,1 ms, 0 % | ❌ latencia |
| `POST /bets/place` p95 (200 VUs/1 mercado) | < 500 ms, 503+5xx < 1 % | 4 321,8 ms, 94,93 % | ❌ ambos |
| `POST /bets/:id/cashout` p95 (ráfaga 200) | < 500 ms, error < 1 % | 127,2 ms, 0 % | ✅ |

Interpretación honesta: el umbral de 500 ms para apuestas **no es alcanzable hoy** ni siquiera
repartiendo la carga entre 48 mercados, y bajo un mercado caliente el sistema elige rechazar
en vez de encolar. Antes de fijar un SLO hay que decidir producto: (a) aceptar 503 como
comportamiento esperado y fijar el SLO sobre la tasa de aceptación, o (b) invertir en el camino
de apuestas para bajar el coste por operación.

## 9. Limitaciones

1. **Sin proxy.** Todo se midió contra Kestrel; nginx y TLS quedan fuera.
2. **Sin saturación de lectura.** El escenario de lecturas va marcado por el `sleep` del cliente.
3. **48 mercados, no 200.** `bet-distinct` reparte 200 VUs entre 48 mercados: hay ~4 VUs por
   mercado, así que no es contención cero.
4. **Ventanas cortas.** 30–60 s por escenario, una sola corrida por escenario: no hay análisis
   de varianza ni de estabilidad en el tiempo.
5. **Host compartido.** k6 (cliente), el contenedor del API y el de PostgreSQL corren en el mismo
   host: Docker Desktop sobre WSL2 con 15,49 GiB y sin aislamiento de CPU. Los porcentajes de CPU
   son del host compartido y el propio generador de carga consume CPU. Las cifras comparan
   escenarios; no son capacidad ni un techo de throughput.
6. **Cash out en ráfaga.** No mide throughput sostenido ni concurrencia repetida.
7. **Ruido de arranque.** Los logs muestran un intento inicial fallido de
   `__EFMigrationsHistory` antes de aplicar migraciones y un aviso por
   `libgssapi_krb5.so.2` ausente; ninguno afecta las mediciones (el escenario corre después del
   arranque completo).
